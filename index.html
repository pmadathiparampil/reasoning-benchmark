How I build a task

Every task ships with four artifacts: the prompt, a step-by-step reasoning chain, a reasoning graph of retrieval and compute nodes, and a weighted rubric.

01 · Source

Pick a hard primary source

Old fixed-width filings, multi-row holdings, split vote records, affiliated registrants. Places where a model has to read the document, not recall a number.

02 · Chain

Force multiple hops

Each answer depends on an earlier retrieval: a filing date feeds a FRED lookup, a computed digit picks a row, an entity has to be resolved across a merger.

03 · Verify

Parse it myself

I write a parser for each source format and reconcile row sums against the filing's own totals before an answer goes in the key.

04 · Grade

Weight the rubric

Final answers carry 50 points, split evenly. Intermediate steps share the other 50, so a lucky final number without the right inputs still loses credit.

TASK 01 · Single-filer, two-quarter comparison

BlackRock 13F-HR: 3M position, Q2 vs Q3 2025

Model missed Q1 and Q2
13F-HR XML info tableFRED SP500Row-level filtering

Compares BlackRock's largest single 3M holding row across two quarters, derives an implied price per share, then pulls the S&P 500 close on the filing date the model has to find for itself.

Why it's hard

  • Asks for the single largest row, not the aggregate position. 3M appears on several rows per filing.
  • The Q3 filing date isn't given. The model has to read it from the EDGAR index page and use it as the FRED lookup key.

Q2 · Implied $/share, Q3 row$155.18model: correct, then regressed

Prompt, reasoning chain and rubric

Prompt (condensed)

BlackRock, Inc. files quarterly 13F-HR reports. The Q2 2025 report was filed 2025-08-12; the Q3 2025 report (period 2025-09-30) was filed on a date recorded on its EDGAR index page. Consider BlackRock's holdings in 3M Company (CUSIP 88579Y101). (1) What was the share count in the single largest Q2 row as a percentage of the single largest Q3 row? (2) What is the implied value per share from that Q3 row? (3) What was the S&P 500's FRED close on the Q3 filing date?

Reasoning chain

  1. LOOKUPQ2 2025 info table, CUSIP 88579Y101, largest row: 15,699,531 shares.
  2. LOOKUPQ3 2025 filing (filed 2025-11-12), largest row: 16,010,436 shares, $2,484,499,458.
  3. CALC15,699,531 / 16,010,436 = 98.06%
  4. CALC$2,484,499,458 / 16,010,436 = $155.18
  5. LOOKUPFRED SP500, 2025-11-12: 6850.92

Model review

First attempt guessed 100% for Q1, which suggests it never located the row-level data. After review it answered 99.3%, still wrong. Q2 was correct on the first run and wrong on the second, which points to an unstable retrieval path rather than a math error.

  1. LOOKUP10-Q (period 2024-09-28) filed 2024-10-30 → DGS10 4.29
  2. LOOKUP10-K (period 2024-12-28) filed 2025-02-05 → DGS10 4.43
  3. LOOKUP9M operating cash $1,742M, PP&E purchases $428M

TASK 03 · Entity resolution across a merger

State Street and Chase Manhattan cross-holdings, 1999

Model missed both answers
Plain-text 13F-HRFixed-width parsingInvestment discretionPre-merger names

Find State Street's earliest two plain-text 13F filings, value its stake in the company that became JPMorgan Chase, then go to that company's own 1999 filing (under its old name) and price its sole-discretion stake in State Street.

Why it's hard

  • The prompt never names Chase Manhattan. The model has to resolve which pre-2000 registrant's CIK became JPMorgan Chase & Co.
  • 1999 filings are fixed-width text with continuation rows and page headers, not XML.
  • Only the 4 of 7 rows flagged sole discretion count.
Q1 · Sole-discretion $/share$85.37model: 85.38 / 85.31

  1. LOOKUPState Street (CIK 93751) earliest plain-text 13F-HRs: period 1999-03-31 filed 1999-05-25; period 1999-06-30 filed 1999-08-06.
  2. LOOKUPChase Manhattan Corp (CUSIP 16161A10) in each: $1,001,189,093 / 12,303,399 and $1,156,782,492 / 13,373,208.
  3. COMPARELater filing is larger, so use Q2 1999.
  4. RESOLVECIK 19617 filed as "CHASE MANHATTAN CORP /DE/" through 2000, then "JPMORGAN CHASE & CO".
  5. LOOKUPChase Q2 1999 13F-HR, filed 1999-08-11. State Street (CUSIP 85747710) spans 7 rows.
  6. CALCSole rows (4): $21,375,000 / 250,367 shares. Shared rows reconcile to the filing's aggregate $25,065,000 / 293,582.
  7. CALC21,375,000 / 250,367 = $85.37 (Answer 1)

Across two runs, the model got nearly every factual anchor wrong, including all three filing dates. Its 85.38 on Q1 looks like a rounding miss, but it came from the wrong inputs (509.1M / 5.963M), which happen to give a similar ratio. The rubric's intermediate rows are what catch this.

TASK 07 · End-to-end analytics, in development

When to switch from a generic to a sequence-specific aftershock forecast

In development
Reasenberg–Jones modelPage et al. (2016)Poisson log-likelihoodBacktest, 10 sequencesCSV + memo + script

A regional hazard office is launching a 90-day aftershock advisory program. After a large quake it issues the published generic forecast, then switches to a forecast re-fitted on that sequence's own aftershocks. The task: backtest switching on day 1, 2, 3 or 7 across ten 2018–2020 sequences and recommend when to switch.

Why it's hard

  • The model has to build the aftershock windows itself: 1.5× the Wells–Coppersmith rupture length (minimum 50 km), within 70 km of mainshock depth, M4.5+, cut short if another M7+ lands inside the window.
  • Each forecast may use only data available on the switch day, so leaking later aftershocks into the fit is an easy mistake.
  • The decision rule is strict: pick the earliest day where the sequence-specific forecast beats the generic one in at least 8 of 10 sequences, otherwise stay generic for all 90 days.
  • Three deliverables have to agree: a 40-row CSV, a one-chart PDF memo for a program lead, and a script that reproduces the CSV and prints the recommendation.
Expected recommendationDay 3possibly day 2
Generic-forecast spread227 vs 45Tari vs Palu, both M7.5
Prompt and reasoned answer

Prompt (condensed)

When a large shallow earthquake strikes, we will immediately issue the published generic forecast for its tectonic region, using the Page et al. (2016) parameters. As aftershocks are recorded, we can replace it with a sequence-specific forecast: the same Reasenberg–Jones model with productivity and decay re-estimated from that sequence. Backtest switch days 1, 2, 3 and 7 on Kodiak (Jan 2018), Tari (Feb 2018), Palu (Sep 2018), Zakynthos (Oct 2018), Loyalty Islands (Dec 2018), Kamchatka (Dec 2018), Kermadec (Jun 2019), Molucca Sea (Nov 2019), Kermadec (Jun 2020) and Sand Point (Oct 2020). Score each forecast of switch-day-to-day-90 counts by Poisson log-likelihood, and recommend the earliest day where the sequence-specific forecast wins in at least 8 of 10 sequences. Deliver a CSV, a short PDF memo with one decision chart, and the reproducing Python script.

The model being tested

Expected rate of aftershocks of magnitude M or above at time t is 10^(a + b(Mmain − M)) × (t + c)^−p. The generic forecast uses fixed regional averages for a, b, p and c, so it gives every quake of the same size in the same region the same forecast.

Reasoned answer: day 3, possibly day 2

  • Why not day 1. One day of data (10–76 aftershocks per sequence) shows productivity but very little about decay. Several sequences would mislead a day-1 fit, which likely means 2–3 failures out of 10 and a miss on the 8-of-10 bar.
  • Kermadec 2019 starts slow: 19 aftershocks on day 1, 21 more over days 2–3, 34 over days 4–7. A day-1 fit assumes fast decay and under-predicts.
  • Palu burns out fast: 29 on day 1, then 4, 5, 6 and 1 in later periods. A day-1 fit with typical decay over-predicts.
  • Kodiak flares up late: 12 aftershocks in days 38–90, more than days 8–37 had.
  • Early undercount: day-1 catalogs miss events in the first hours after the mainshock.
  • Why day 3 passes. The decay shape starts to show, and the re-fit fixes the generic forecast's biggest error, the productivity level, in most sequences.
  • Why not day 7. It probably passes too, but the rule picks the earliest passing day, and by day 7 most aftershocks have already happened.

Status: prompt and expected answer drafted; the backtest script and rubric are in progress.

Parsing toolkit

I build a parser for every source format before writing an answer key. Each one reconciles its output against the filing's own totals and flags rows it can't trust.

parse_13f_html.py

Full toolkit for modern XML-rendered 13F information tables: row lookup by position, CUSIP and issuer aggregation, top/bottom-N ranking, put/call and discretion breakdowns, cross-filing comparison.

Finds the real header row by its "NAME OF ISSUER" label and skips the decorative "COLUMN 1…" rows above it. Warns that row values are in dollars while the Summary Page total is in $000s.

Used in tasks 01, 04, 06

parse_13f_text_chase.py

Regex parser for pre-2013 fixed-width plain-text 13F tables, handling first rows and the "0"-prefixed continuation rows that carry a holding across lines.

Reports lines that look like data but match neither pattern, so possible undercounts are visible instead of silent.

Used in tasks 03, 05

analyze_13f_text_chase.py

Two-filing analyzer: assigns every data row a physical row index, finds the smallest row per CUSIP, and computes the ratio and implied-price answers.

Reads the VALUE unit from the header by matching only the parenthesized token directly before "AMOUNT", which avoids the "(SHARES)" decoy on the line above.

Used in task 05

parse_13f_text_statestreet.py

Parser for State Street's 1999 fixed-width tables with two three-way splits per row: investment discretion and voting authority.

Re-reads column positions from each page's own header instead of hardcoding them, since an $8.7B row formats wider than a $1 row. Every row is sum-checked, and genuine source-filing errors (a BellSouth row off by 20,198 shares) are flagged rather than "fixed".

Used in task 03

npx_pipeline.py

Bridgewater Form N-PX proxy-vote pipeline: labels every row and every split FOR/AGAINST sub-outcome, aggregates by issuer, and walks forward through FRED DGS10 by a computed digit.

Reports both counting definitions (per table row and per vote outcome) so the rubric can lock one in explicitly.

N-PX task, write-up in progress

npx_final.py · npx_independent_walk.py

Two competing interpretations of the same N-PX digit-walk prompt, built to test whether the prompt is ambiguous before it ships.

Found that one zero-share row with no recorded vote (Masimo) changes the total from 892 to 891 and moves the landing row. The final version counts it as zero entries.

N-PX task, write-up in progress

compare.py

Token-level diff between two versions of a prompt or answer, printed with context and saved as a highlighted HTML report.

Tokenizes on words, whitespace and single punctuation marks, so a changed digit or comma inside a number shows as its own edit.
